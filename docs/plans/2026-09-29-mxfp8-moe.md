# Native MXFP8 MoE implementation plan

## Goal

Serve the Qwen3.8-Flash-Next-NVFP4 step5500 MTP experts through the B12X backend without converting their MXFP8 weights to FP4, FP6 or BF16 storage. Reuse the existing block-scaled MMA and grouped MoE execution model.

## Source contract

The checkpoint declares 512 experts, hidden width 2560, intermediate width 640 and top-k 10. Each gate/up projection stores E4M3 values with UE8M0 scales over 32 K elements. The canonical source is `MXFP8_E8M0_K32 = "mxfp8_e8m0_k32"`. A8 planning selects the private `w8a8_mx` recipe. Preserve weight and scale bytes. Reuse the existing MXFP8 scale-layout definition rather than introduce another swizzle.

## Tracked implementation

- [x] Extend `moe/fused_moe/source.py`, `planning.py`, `weights.py` and `moe/_shared/execution.py` with the format, encodings and preparation transform. Verify lossless packing and scale geometry on CPU before GPU execution.
- [x] Extend `moe/_shared/kernels/dynamic.py`, `moe/fused_moe/_impl.py` and `_tuning.py`. Reuse FP6 byte-width activation staging but read E4M3 weights directly. Audit packed-K assumptions, stage memory, route tails and launcher identities. `_preparation.py` already handles these declarations generically.
- [x] Integrate the vLLM fork through `oracle/mxfp8.py`, `oracle/fp8.py`, the B12X experts adapter and ModelOpt post-load conversion. Do not add a competing FP6-plugin route. Preserve immutable input-scale ownership, NVFP4 targets and draft-only backend selection.
- [x] Run host contracts, bounded numerical GPU tests, prepared CUDA graph replay and Compute Sanitizer. Inspect generated device objects for the `sm_120f` family target. Re-run the unchanged NVFP4 baseline.
- [ ] Publish paired implementation branches and document measured results and remaining runtime prerequisites.

## Verification constraints

GB10 hosts run live workloads and must not be touched. The user permits a separate RTX PRO 6000 SM120 host. That host also runs a live vLLM engine. Do not stop or change it. Use an isolated container and reduced expert count with real projection widths. The runner admits work only with at least 4 GiB free VRAM and caps the PyTorch allocator at 1 GiB. Inspect planned scratch requirements before launching. No full model load while this engine occupies the card.

Use `sm_120f`, which covers SM120 and SM121. Execution on the approved card proves SM120 behaviour only. ISA documentation proves instruction legality, not compiler output or execution.

Compiled programs live in the approved host's `scratch/mxfp8-moe-validation/compile` directory on ext4, bind-mounted into each isolated container as `/validation/compile`. Container removal does not destroy those bytes. Host filesystem loss or explicit directory removal does. Claim persisted reuse only after recreating the consumer container and observing a disk-cache hit.

Full step5500 serving, acceptance-rate and Marlin latency comparisons require a separate memory-capacity window. Do not replace these measurements with historical results from a different revision. No performance claim without representative serving evidence and clock/power telemetry.

## Baseline evidence

On the unchanged B12X `b7f8879a` source, the selected CPU MoE lane gives 19 passed, 7 skipped and 2 failures. Both failures are existing calls to `plan_tp_moe_execution` missing `decode_config`. The small NVFP4 GPU preparation test passes on the approved SM120 card with a 344576-byte peak PyTorch allocation. Two retained NVFP4 decode/replay cases pass with a 42538496-byte peak allocation. A recreated consumer container runs these cases with 36 disk-cache hits and zero compile misses.

## Native execution evidence

The full MXFP8 bounded lane passes 21 tests. Compute Sanitizer memcheck passes
the six numerical/replay cases with zero errors. Emitted device-object metadata
records `-arch sm_120f`; disassembly contains
`QMMA.SF.16832.F32.E4M3.E4M3.E8`. Native numerical tests cover M=1/5/16,
empty experts, atomic replay versus the quantized oracle and deterministic
bit-exact replay. A recreated container records 13 disk-cache hits and zero
compile misses for the full suite.

The real vLLM ModelOpt lifecycle passes on CUDA with world-size-one NCCL
initialization, source-weight loading, native preparation, declared execution
and reference-output comparison. Peak PyTorch allocation is 862,021,632 bytes,
below the 1 GiB lane cap. The draft override path passes three tests.

The retained NVFP4 lane passes three tests after the change. Peak allocation
remains 42,538,496 bytes, equal to the original baseline. CPU recipe-independent
planning passes 16 tests after fixing the two stale explicit-config fixtures.
